What this is (and what it isn't)

✅ Goal

Multiple real Next.js dashboard apps that share a monorepo foundation. Client A, B, C each get their own application.

❌ Not this

One dashboard with tenant-specific configuration branches. Not a modular monolith with per-client folders.

Share the foundation, not the application. A change to Client A's app never requires touching Client B's. A change to @zosma/ui flows to clients through normal package versioning — deliberately, not by accident.
Architecture

Next.js Multi-Zones in a monorepo

A "zone" is an independently deployed Next.js app. Each client dashboard is its own zone. Applications share packages but never share app code.

Why not one huge Next.js app?

A modular monolith (apps/dashboard/client-a/…) is simpler at first, but as clients diverge it rot:

↔
client code becomes coupled
↑
build times grow with every client
⚠
one deploy affects everyone
?
ownership boundaries blur

Real application-level isolation (apps/client-a, apps/client-b) keeps build → test → deploy independent per client.

Why not make everything a microfrontend?

Low-level building blocks stay shared packages, not runtime-deployed microfrontends:

ButtonCardModalTableChartDatePickerNavigationAuth utilsAPI client

Zone/microfrontend boundaries belong at the application or major product-module level — where independent deployment and ownership actually add value.

Routing

Composing apps into one experience

Multi-Zones is about how multiple apps are routed/composed into a single web experience. Three deployment models.

Option A — Path-based

zosma-dashboard.com/client-a/*
zosma-dashboard.com/client-b/*
zosma-dashboard.com/client-c/*
  • ✅ one domain, centralized branding, identity encoded in path
  • ⚠ each app must work under a path prefix; assets/base paths need care; cross-zone nav is a hard navigation

Option B — Subdomain-based

client-a.zosma-dashboard.com
client-b.zosma-dashboard.com
client-c.zosma-dashboard.com
  • ✅ strong app boundary; each app owns /; clean identity/branding per client
  • ⚠ DNS management; cookies/auth need deliberate design; more hostnames

Recommended default when clients are truly independent.

Option C — Customer-owned custom domains

dashboard.acme.com
portal.globex.com
  • ✅ best white-label; client sees its own domain
  • ⚠ DNS onboarding, TLS cert management, domain verification — operational complexity

Add later; does not change the core app model.

Routing layer concept

Deployment

Same pattern, any infra

Next.js Multi-Zones is an architectural pattern, not a Vercel product. Each app is a normal Next.js deployment; only the routing/hosting layer differs.

Vercel — one project per client

Vercel's Microfrontends tooling can supply the routing/composition layer. Each client is a separate Vercel project. Core choice (independent apps) stays the same; Vercel just changes the hosting layer.

GCP deployment

Vercel ≠ the architecture. The idea is just multiple Next.js apps + routing between them. Same pattern runs on Vercel, GCP, AWS, Cloudflare, Kubernetes, or nginx. Vercel only adds managed microfrontend tooling.
Decisions

Multi-Zones vs Module Federation

Choose the composition boundary that matches reality. Zosma has many separate client dashboards — that's an application/route-level concern, not a runtime component one.

✅ Multi-Zones (fits Zosma)

Each app owns its routes. Composition at the application/route level. Each client is an independent dashboard — this matches.

App A → owns routes A
App B → owns routes B

◻ Module Federation

Runtime component-level composition: a host dynamically loads remote components. Useful when one app assembles independently deployed modules. Not needed just because there are many dashboards.

host → loads remote A
host → loads remote B
host → loads remote C

Next.js implementation checklist

  • Routing: decide path-based, hostname-based, or both.
  • Base paths: for path-based zones, ensure the app handles its prefix correctly.
  • Cross-zone navigation: it's a hard navigation, not a client-side transition. Intra-app nav stays normal.
  • Auth: shared across apps, isolated per client, or central IdP. Don't assume cookies/session work across unrelated domains.
  • Shared UI versions: a client must not break because @zosma/ui changed. Manage via package versioning.
  • Independent deploy: build → test → deploy per client, no other client in the path.
Prefer current Next.js App Router docs over older tutorials based on Next 12–14 or legacy React/Module Federation examples.
Mental Model

The summary to hold in your head

Six statements that capture the whole architecture.

  • Shared code ≠ shared application.
  • Separate apps ≠ separate domains.
  • Multi-Zones ≠ Vercel.
  • Vercel = managed tooling for the same architecture.
  • GCP can implement the routing layer independently.
  • Don't add Module Federation until runtime component composition is a real need.

Recommended starting point

Start with Option 1 (subdomain) — client-a.zosma-dashboard.com — when dashboards are truly separate apps. Use path-based if a single canonical domain matters more. Add customer-owned domains when white-label becomes important.
